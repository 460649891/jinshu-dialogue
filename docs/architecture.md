# 采集与桌面界面

项目只适配 `profiles/jshyl-5.60c.json` 中的主程序，监听过程不改写游戏文件或存档。Frida 的 `Interceptor` 会临时改动进程内的入口指令以安装钩子，停止采集后解除连接。因此这里的“读取对白”不等于完全不改变进程内存。

## 一条对白如何到达界面

```text
游戏进入对白函数 → 为本次调用分配 sequence
  → 同一对白对象绘制人物名 → 绘制完整正文
  → 一条包含 speaker + text 的原子事件
  → Frida 回调放入有界队列
  → Python 按 GB18030 解码、按 session/sequence 去重
  → 刷新 TXT + JSONL 文件 → Qt 信号 → 每 100 ms 批量更新列表
```

可以把它理解为 Java 中的事件生产者、`BlockingQueue`、后台消费者和 UI 线程。Frida 回调只入队，不负责磁盘或界面；队列满时明确停止并报错，避免阻塞游戏线程或悄悄丢记录。文件按次创建，不覆盖已有记录。每条写入后 flush；这降低异常退出时的丢失范围，不代表已经执行磁盘 fsync。

`src/capture.py` 提供 `CaptureService.run(stop_event, on_status, on_dialogue)`。`src/dialogue.py` 不依赖 Qt 或 Frida，负责转换和持久化；`src/gui.py` 中的工作线程负责启动采集、发信号及响应停止。停止信号通过 Frida Cancellable 取消等待中的调用。窗口关闭时先等待采集结束，不销毁仍在运行的 QThread。

## 去重与人物配对

画面重绘次数不能代表新对白数量；对 `(人物名, 文字)` 永久去重又会误删剧情中确实重复的一句。当前实现以真正的对白函数调用作为边界：每次调用建立独立状态，分配递增序号，第一次正文绘制输出一条事件。后续重绘不再输出；下一次调用即使文字相同也会输出。

人物名从同一次调用、同一个对白对象的绘制中读取，不依赖文字在屏幕上的坐标。上一次调用的名字不会传入下一次；没有名字时显示“未知人物”。状态按线程和嵌套调用维护，重连后更换会话标识。启动时已显示的对白可能没有经过新安装的入口钩子，因此从下一句开始采集。

适配配置包含 SHA-256、函数相对地址和入口签名。先校验磁盘程序，再校验进程路径、架构和入口字节。其他版本应重新调查与验证，直接改哈希或地址没有兼容保证。特殊窗口走不同函数时需要另外适配。

## 阅读与发布

列表采用 Qt model/view，最多保留最近 2,000 条，完整记录持续保存在文件中。向上滚动后保留阅读位置和选择，仅更新新增提示；复制和导出使用原始正文，不使用列表摘要。演示模式使用原创文字，不连接游戏。

PyInstaller 构建为 `onedir`，Qt、Python 和 Frida 随 `_internal` 一起分发，不依赖接收者安装 Python。源码 ZIP 使用允许清单，排除个人路径设置、游戏、诊断、对白记录及开发环境。第三方许可证通过已校验的本地缓存离线收集，来源见 `scripts/licenses/SOURCES.json`。
